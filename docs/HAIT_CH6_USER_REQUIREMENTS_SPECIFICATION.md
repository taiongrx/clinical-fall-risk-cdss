## 1. บทนำและที่มาของปัญหา (Background & Problem Statement)

### 1.1 ที่มาและปัญหาทางคลินิก
* ภาวะการหกล้มในผู้ป่วยสูงอายุ (อายุ 60 ปีขึ้นไป) เป็นสาเหตุสำคัญที่ทำให้เกิดความพิการ การบาดเจ็บรุนแรง (กะโหลกศีรษะแตก เลือดออกในสมอง กระดูกสะโพกหัก) และการเสียชีวิต
* เดิมการประเมินความเสี่ยงใช้แบบประเมิน Morse Fall Scale (MFS) ซึ่งมีข้อจำกัด:
  1. ใช้เวลาในการสอบถามและกรอกข้อมูลสูง ทำให้เกิดความล่าช้าในจุดคัดกรองที่มีผู้รับบริการหนาแน่น
  2. มีความแปรปรวนระหว่างผู้ประเมิน (Inter-rater variability)
  3. ไม่สามารถวิเคราะห์และตรวจจับรายการยาที่ผู้ป่วยได้รับจริงในอดีต (Fall-Risk-Increasing Drugs: FRIDs) ได้อย่างครอบคลุม
* **ความต้องการทางคลินิก:** ต้องการระบบสนับสนุนการตัดสินใจทางคลินิก (CDSS) ที่สามารถเชื่อมต่อฐานข้อมูลเวชระเบียน HOSxP ได้แบบ Real-Time คำนวณความเสี่ยงด้วยปัญญาประดิษฐ์ (AI Machine Learning) และแจ้งเตือนจุดเสี่ยงพร้อมแผนการดูแลรักษาแบบอัตโนมัติ

## 2. การวิเคราะห์ผู้มีส่วนได้ส่วนเสียและสิทธิ์การใช้งาน (Stakeholder Matrix & RBAC)

ตามเกณฑ์ HAIT 6.1 ระบบต้องมีการจำแนกสิทธิ์และความต้องการตามบทบาทหน้าที่ (Role-Based Access Control):

| บทบาทผู้ใช้งาน (Role) | ความต้องการหลักในการใช้งานระบบ (Key User Needs) | สิทธิ์ในระบบ (Access Level) |
|---|---|---|
| **พยาบาลคัดกรอง (OPD/IPD Nurse)** | • ดูรายชื่อผู้ป่วยสูงอายุที่จุดคัดกรองแบบ Real-Time<br>• ดูระดับความเสี่ยง (High Risk / Lower Risk) และค่า Probability<br>• บันทึกเช็กลิสต์การพยาบาล (Nursing Care Plan)<br>• บันทึกผลการติดตามการหกล้มจริง (Fall Outcomes) | สิทธิ์บันทึกและประเมิน (Clinical Evaluator) |
| **เภสัชกร (Pharmacist)** | • ตรวจสอบรายการยาเสี่ยงล้ม (FRIDs) ที่ผู้ป่วยกำลังใช้อยู่<br>• ปรับปรุงการจับคู่รหัสยา TMT, GPU และ WHO-ATC (ATC Drug Mapping)<br>• จำลองและเสนอปรับเกณฑ์ Decision Threshold ของโรงพยาบาล | สิทธิ์ผู้เชี่ยวชาญยา (Clinical Pharmacist / Admin) |
| **แพทย์ (Physician)** | • ดูคะแนนความเสี่ยงและปัจจัยเสี่ยงประกอบการสั่งใช้ยา<br>• ปรับเปลี่ยนยาในกลุ่ม FRIDs ไปใช้ยาทางเลือกที่ปลอดภัยกว่า | สิทธิ์ดูข้อมูลประเมิน (Clinical Viewer) |
| **ผู้ดูแลระบบไอที (IT Administrator)** | • ตรวจสอบสถานะ Server, Database, Background Daemon<br>• สำรองข้อมูลและกู้คืนระบบตามแผน BCP/DRP<br>• ควบคุมการเปลี่ยนผ่านเวอร์ชันซอฟต์แวร์ (Version Control) | สิทธิ์บริหารระบบเต็มรูปแบบ (System Admin) |
| **ผู้ตรวจประเมินคุณภาพ (HA / Auditor)** | • ตรวจสอบ Audit Trails, ประวัติการประเมินย้อนหลัง<br>• ตรวจสอบความสอดคล้องตามเกณฑ์ PDPA และ HAIT บทที่ 6 | สิทธิ์ตรวจสอบ (Auditor / Read-Only Analytics) |

## 3. ข้อกำหนดความต้องการเชิงหน้าที่ (Functional Requirements: FR)

### FR-01: การคัดกรองผู้ป่วยสูงอายุอัตโนมัติ (Automated Screening Daemon)
* **FR-01.1:** ระบบต้องมี Background Daemon ตรวจจับผู้ป่วยอายุ $\ge 60$ ปี ที่มารับบริการ ณ แผนกผู้ป่วยนอก (OPD) จากตาราง `ovst` ของ HOSxP ได้แบบ Real-Time (รอบการตรวจจับ $\le 30$ วินาที)
* **FR-01.2:** ระบบต้องคัดกรองและประเมินความเสี่ยงล่วงหน้าทันทีที่ผู้ป่วยลงทะเบียน เพื่อให้ผลคะแนนพร้อมแสดงผลเมื่อผู้ป่วยมาถึงจุดคัดกรอง/ห้องยา

### FR-02: การคำนวณความเสี่ยงด้วยโมเดล Machine Learning (AI Inference)
* **FR-02.1:** ระบบต้องใช้โมเดล BalancedBagging LightGBM หรือ Tabular Neural Network ที่ผ่านการฝึกฝนจากข้อมูลเวชระเบียนจริง
* **FR-02.2:** ระบบต้องดึงข้อมูลตัวแปรทางคลินิกย้อนหลังอัตโนมัติ:
  * ประวัติยาเสี่ยง FRIDs 12 กลุ่ม ย้อนหลัง 365 วัน
  * ประวัติการวินิจฉัยโรคตาม ICD-10 (กลุ่มเสี่ยงทางระบบประสาท, หลอดเลือดสมอง, ข้อเสื่อม ฯลฯ) ย้อนหลัง 10 ปี
  * สัญญาณชีพ ค่าดัชนีมวลกาย (BMI) และผลตรวจทางห้องปฏิบัติการ (eGFR, Cr, HbA1c ฯลฯ)
* **FR-02.3:** ระบบต้องแสดงผลคะแนนความน่าจะเป็น (Risk Probability 0–100%) และระดับความเสี่ยง (High Risk เมื่อคะแนน $\ge 0.47$, Lower Risk เมื่อคะแนน $< 0.47$)

### FR-03: การแสดงรายการปัจจัยเสี่ยงและรายการยา FRIDs (Explainable CDS)
* **FR-03.1:** ระบบต้องแสดงรายการ Active Risk Factors แยกตามหมวดหมู่ (ยาเสี่ยงล้ม, โรคประจำตัว, และข้อมูลกายภาพ)
* **FR-03.2:** ระบบต้องแสดงชื่อการค้า, ชื่อสามัญ, ขนาดยา, และกลุ่มยา FRID เพื่อให้เภสัชกรและแพทย์นำไปใช้วางแผน Deprescribing ได้ทันที

### FR-04: แผนการพยาบาลและการจัดการความเสี่ยง (Nursing Care Plan)
* **FR-04.1:** ระบบต้องมีเช็กลิสต์การพยาบาล (Nursing Intervention Checklist) เช่น การผูกริสแบนด์สีเหลือง, การให้ความรู้ญาติ, การจัดไม้เท้า/รถเข็น, การประเมินสภาพแวดล้อม
* **FR-04.2:** ระบบต้องบันทึกผู้ประเมินและเวลาที่ประเมินเพื่อความรับผิดชอบทางวิชาชีพ

### FR-05: การบันทึกและติดตามผลลัพธ์จริง (Ground Truth Outcome Feedback)
* **FR-05.1:** ระบบต้องรองรับการบันทึกผลติดตามว่าผู้ป่วยหกล้มจริงหรือไม่ (Did Fall: Yes/No, วันที่เกิดเหตุ, สถานที่, และระดับความรุนแรง)
* **FR-05.2:** ข้อมูล Outcome ต้องถูกเก็บลงตาราง `fall_outcomes` ของ PostgreSQL เพื่อใช้เป็นชุดข้อมูลสำหรับฝึกฝนโมเดลใหม่ในอนาคต

### FR-06: การเชื่อมโยงรหัสยามาตรฐาน TMT $\rightarrow$ GPU $\rightarrow$ WHO-ATC อัตโนมัติ (Version 1.3.0)
* **FR-06.1:** ระบบต้องสามารถเชื่อมต่อโครงสร้าง TMT Hierarchy ใน HOSxP (`drugitems_tmt_tpu_list` $\rightarrow$ `tmt_gpu_to_tpu` $\rightarrow$ `tmt_gpu_code`) เพื่อแปลงเป็นรหัสและชื่อ GPU อัตโนมัติ
* **FR-06.2:** ระบบต้องค้นหาและจับคู่รหัส WHO-ATC ผ่าน NIH NLM RxNav REST API แบบ Batch Process
* **FR-06.3:** ระบบต้องบันทึกผลการจับคู่ลงตาราง `drug_atc_mappings` ภายในโรงพยาบาล เพื่อให้หน้างานประเมินผลได้แบบ Offline 100%

### FR-07: การเรียนรู้และอัปเดตโมเดลอย่างต่อเนื่อง (Continuous MLOps Pipeline)
* **FR-07.1:** ระบบต้องนับจำนวนข้อมูลผลลัพธ์จริง (New Outcomes) สะสม เมื่อครบตามเกณฑ์ที่กำหนด (Auto-Retrain Threshold เช่น 50 เคส) ระบบต้อง Trigger การ Retrain อัตโนมัติ
* **FR-07.2:** ระบบต้องมี Safety Gate ตรวจสอบค่า ROC-AUC ของโมเดลใหม่ หากค่า AUC ผ่านเกณฑ์และสูงกว่าโมเดลเดิม จึงจะอนุมัติให้ Hot-reload ขึ้นใช้งาน

## 4. ข้อกำหนดความต้องการที่ไม่ใช่เชิงหน้าที่ (Non-Functional Requirements: NFR)

### NFR-01: ประสิทธิภาพและเวลาตอบสนอง (Performance & Latency)
* **NFR-01.1:** เวลาในการประมวลผลพยากรณ์ความเสี่ยงต่อคนไข้ 1 ราย (Single Patient Inference) ต้องน้อยกว่า **1.5 วินาที**
* **NFR-01.2:** หน้า Web UI Dashboard ต้อง Render ข้อมูลเสร็จสิ้นภายใน **2 วินาที** ภายใต้โหลดผู้ใช้งานพร้อมกันอย่างน้อย 20 Concurrent Users

### NFR-02: ความพร้อมใช้งานและความทนทาน (Availability & Reliability)
* **NFR-02.1:** ระบบต้องมีความพร้อมใช้งาน (System Uptime) ไม่น้อยกว่า **99.5%** ในเวลาทำการของโรงพยาบาล (07:00 – 17:00 น.)
* **NFR-02.2:** ระบบต้องรองรับการ Restart และกู้คืนตัวเองอัตโนมัติ (Docker Auto-restart Policy) เมื่อเกิดข้อผิดพลาด

### NFR-03: ความมั่นคงปลอดภัยและการปฏิบัติตามกฎหมาย (Security & PDPA Compliance)
* **NFR-03.1 (PDPA มาตรา 26):** ระบบต้องไม่ส่งข้อมูลอ่อนไหวพิเศษ (ข้อมูลสุขภาพ, โรคประจำตัว, ผลแล็บ) ออกไปยังเซิร์ฟเวอร์ภายนอกโรงพยาบาล การประมวลผล AI ต้องเกิดขึ้นภายในเครื่อง On-Premise เท่านั้น
* **NFR-03.2 (Zero Raw PII in Logs):** ในระบบ Logging (Console/File) ห้ามบันทึกเลขบัตรประชาชน 13 หลัก, ชื่อนามสกุล หรือข้อมูลระบุตัวตนดิบของผู้ป่วย
* **NFR-03.3 (Authentication & Brute Force Guard):**
  * เจ้าหน้าที่ต้องยืนยันตัวตนผ่านบัญชี HOSxP ที่มีอยู่จริงในตาราง `opduser`
  * มีระบบตรวจจับและระงับการล็อกอินผิดพลาดเกิน 5 ครั้ง (Account Lockout 15 นาที) เพื่อป้องกันการโจมตีแบบ Brute Force
  * เซสชันการใช้งานต้องเข้ารหัสด้วย JWT (JSON Web Token) โดยมีอายุการใช้งาน 8 ชั่วโมง

### NFR-04: การแยกส่วนและไม่รบกวนฐานข้อมูลหลัก (Read-Replica Isolation)
* **NFR-04.1:** การดึงข้อมูลจาก HOSxP ต้องทำผ่าน **Read-Replica หรือ Staging DB** เท่านั้น ห้ามยิง Query วิเคราะห์หนักๆ เข้า Database Master เด็ดขาด เพื่อป้องกัน Table Lock กระทบงานจ่ายยาและบริการผู้ป่วย

### NFR-05: การปฏิบัติตามมาตรฐานข้อมูลสากล (Interoperability & Standards)
* **NFR-05.1:** รองรับรหัสโรค ICD-10 และ ICD-10-TM
* **NFR-05.2:** รองรับรหัสยามาตรฐานไทย TMT (TPU/GPU), รหัสยา 24 หลัก สปสช. (DID) และรหัสสากล WHO-ATC

## 5. การตรวจสอบความสอดคล้องและเกณฑ์การตรวจรับ (Traceability Matrix & UAC)

| รหัสข้อกำหนด (Req ID) | ฟังก์ชันที่รองรับ | วิธีการทดสอบตรวจรับ (Verification Method) | ผลการตรวจรับ (Acceptance Status) |
|---|---|---|---|
| **FR-01** | Automated Screening | ตรวจสอบการไหลของข้อมูลผู้ป่วยสูงอายุ OPD เข้าสู่ Dashboard ภายใน 30 วินาที | ✅ ผ่าน (Verified via Daemon Status) |
| **FR-02** | ML Fall Risk Model | ตรวจสอบค่า Sensitivity $\ge 90\%$ และ Specificity $\ge 80\%$ ด้วย Validation Set | ✅ ผ่าน (Sensitivity 90.9%, Specificity 83.3%) |
| **FR-03** | FRID Drugs CDS | ทดสอบดึงผู้ป่วยที่ใช้ยา Diazepam, Amitriptyline ตรวจสอบว่าระบบจัดกลุ่มเสี่ยงถูกต้อง | ✅ ผ่าน (Verified with actual EMR) |
| **FR-04** | Nursing Care Plan | ทดสอบบันทึก Checklist การพยาบาล และตรวจสอบการจัดเก็บใน Database | ✅ ผ่าน (Persisted in PostgreSQL) |
| **FR-05** | Outcome Feedback | ทดสอบบันทึกเคสหกล้มจริง และตรวจสอบว่าข้อมูลถูกส่งเข้า Training Pool | ✅ ผ่าน (Audited via MLOps View) |
| **FR-06** | TMT/GPU to ATC API | ทดสอบฟังก์ชัน Auto-Resolve TMT กับยาในคลัง ตรวจสอบการจับคู่ WHO-ATC ผ่าน RxNav | ✅ ผ่าน (Release v1.3.0 Verified) |
| **NFR-01** | Latency & Speed | ทดสอบยิง API Benchmark เวลาประเมินผลเฉลี่ย | ✅ ผ่าน (เฉลี่ย 320 ms ต่อคนไข้) |
| **NFR-03** | PDPA & Security | สแกน Log File ตรวจสอบว่าไม่มีเลขบัตรประชาชน 13 หลักหลุดรอด | ✅ ผ่าน (Zero PII Confirmed) |
